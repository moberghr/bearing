# Codebase review — 2026-07-23

Full-codebase review (code style, architecture, maintainability, separation of concerns,
spaghetti, god objects, unclear paths). Findings below are grouped by severity and tagged
with status as they are addressed. Work is on branch `review-fixes`.

## Verdict

Layering is sound: dependency direction is clean and structurally enforced (`Core` → nothing;
`Sql`/`Data`/`Persistence` → `Core` only; `App` composes; `Desktop` thin). The `Input/` pipeline
and the pure `Sql`/`Results` helpers are well-factored. The problem is the recent "refactor" only
half-landed: the **ViewModel** side was genuinely decomposed, but the two biggest UI classes were
split into partial *files* without extracting anything — same tangle, hidden line count.

## Correctness bugs

- [x] **#1 — Paging/count wrap breaks on duplicate column names — REJECTED (false positive).**
  Verified against live PostgreSQL 17.9: `select *` and `count(*)` over a duplicate-column derived
  table (`select a.*, b.* from a join b`) both work — PG permits duplicate output column names in a
  subquery and only errors if you *reference* the ambiguous name. `ExecutePageAsync`/`CountAsync` are
  fine. No change.
- [x] **#1b — Paging used two SQL shapes per result set (real, found in QA).** Page 1 appended a
  top-level `LIMIT` (`FirstPageLimiter`) but load-more wrapped in a subquery. A top-level LIMIT
  guarantees the query's `ORDER BY`; a subquery wrap doesn't — so ordering could diverge at the
  page-1/page-2 seam (duplicated/skipped row). Fixed: `FirstPageLimiter.TryAppendPage(sql, offset,
  limit)` (shared safety check with `TryAppendLimit`); `IQueryExecutor.ExecutePreparedPageAsync`
  runs the pre-suffixed SQL with no wrap; `ExecutePageAsync` (wrap) stays as the fallback for queries
  that can't take a safe suffix. `LoadMoreAsync` now appends when safe, wraps otherwise — same shape as
  page 1. Layering respected: the append-vs-wrap decision lives in `App` (sees both `Sql` + `Data`).
  Tests: +14 `FirstPageLimiterTests`, +1 live `PostgresExecutorTests` asserting prepared-page paging
  is in-order and matches the wrap row-for-row (ran live, 0 skipped).
- [x] **#1c — All paging SQL generation consolidated in `Bearing.Sql` (QA follow-up).** The first
  pass left the wrap being built inside `Bearing.Data` while the append was in `Sql` — SQL generation
  split across two layers, inconsistent with the codebase's own rule (`DmlGenerator`/`TableDdlGenerator`
  generate SQL in `Sql`; `Data` executes). Fixed: new pure `Bearing.Sql/PageSql` owns both shapes
  (`Page` = append-when-safe-else-wrap, `Wrap` = derived table); `IQueryExecutor` collapsed to a single
  `ExecutePageAsync(pageSql, ct)` that just runs the string; the App calls `PageSql.Page(...)`. `Data`
  no longer knows any paging shape. Tests: +7 `PageSqlTests` (append vs wrap decision, wrap string);
  Data paging tests rewritten to feed the executor literal page SQL (both shapes, still live).
- [x] **#2 — Global hotkeys fire under the write-confirm panel.** Fixed: `OnKeyDown` now swallows every
  global shortcut under `_pendingScriptOverlay` except Escape (which still reaches `HandleEscape` to
  close the panel); `OnWindowNavKey` blocks all nav commands while it's open.
  - **#2b (QA follow-up) — Tab focus escaped the overlay to the toolbar behind it.** Our command
    dispatcher suppression doesn't cover Avalonia's Tab focus traversal. Fixed with a focus trap:
    `KeyboardNavigation.TabNavigation = Cycle` on each overlay host (palette + quick-pick via `FillHost`;
    pending panel made focusable + focused on open so the trap engages). Tab now cycles within the
    overlay only. Needs user QA.
- [x] **#3 — Shutdown race leaks an Npgsql pool.** Fixed: `_disposed` flag set under `_gate` in
  `DisposeAsync`; `BuildAsync` drops+disposes the freshly built session instead of repopulating `_live`,
  and `GetOrConnectAsync` throws `ObjectDisposedException` once disposed.
- [x] **#4 — Session resume state can be truncated on crash.** Fixed: sync `Save` now writes tmp+`Move`.
- [x] **#5 — `SqliteQueryLog.DisposeAsync` calls `ClearAllPools()`.** Removed (safe on Linux; the 13
  Persistence tests, including reopen-after-dispose, still pass).

## Spaghetti / unclear paths (deferred)

- [x] **`_keyTarget` hidden implicit parameter for grid commands — resolved.** The grid commands
  (copy / select-all / delete / begin-edit) are registered once in the shared registry and read a target;
  the old `_keyTarget` field was set only by a grid keystroke yet **persisted** after it, so a grid command
  invoked from the command palette (which shares the registry) acted on a stale/last-keyed grid. Fixed by
  (a) `_keyStrokeTarget` — published for the duration of a single `OnGridKey` dispatch only, cleared in a
  `finally` (grid commands are synchronous, so they read it inside `TryHandle`); and (b) a `GridTarget()`
  resolver that returns the keystroke's grid when a key is in flight, else the grid owning the current
  selection (new `_gridsByResult` map). Keystroke path is byte-identical; **palette-invoked grid commands
  now act on the current selection instead of a lingering field.** Solution builds 0/0, 142 App tests
  green. **Palette-path behavior is a change — needs eyeball QA** (invoke Copy/Delete/Edit from the palette
  with a selection active vs. none).
- [x] **`async void` fire-and-forget driven by property setters in `ConnectionsViewModel` — resolved.**
  `RefreshTabDatabases`/`WarmConnection` were `async void` reached from the `SelectedTabConnection`/
  `SelectedTabDatabase` setters and the tab-changed hook, so a fault in their synchronous preamble could
  escape to the sync context (crash) with no way to observe it. Both are now `…Async` returning `Task`,
  invoked through `CrashReporter.Observe(task, context)` (the codebase's existing observed-fire-and-forget
  sink) at all six call sites. Each method keeps its own intentional inner catch — the offline DB-list
  fallback and warm's quiet-on-failure must *not* surface — so only unexpected preamble faults are now
  logged. No behavior change on the happy path. Solution builds 0/0, 142 App tests green. (Also switched
  the extracted overlay's `TextBox.Watermark` → `PlaceholderText`, clearing a pre-existing obsolete-API
  warning.)
- [x] **Delegate-web coupling between extracted VMs — resolved.** `WorkspaceViewModel`'s ctor took four
  loose `Action`/`Func` callbacks (`refreshScripts`, `updateTitle`, `applyConnectionDisplay`,
  `renameScript`) — opaque about what it actually collaborated with. They resolved to just two sibling VMs
  plus one shell method. Now the ctor is `(WorkspaceContext, ScriptsViewModel, ConnectionsViewModel)`: it
  holds the two siblings directly (already built before it, no back-reference → no cycle) and calls their
  real methods. The `updateTitle` callback was **dropped** — `UpdateTitle` sets the title from the project
  name only, so the two calls in open/save-script were no-ops (a script never changes the project-name
  title). 4 delegates → 0; dependencies are now typed and self-documenting. Solution builds 0/0, 142 App
  tests green; no UI QA needed (pure VM wiring, behavior unchanged).
- [x] **Five copies of the CTS/`IsBusy` dance in `ExecutionViewModel` → `RunExclusiveAsync` helper.** All
  five async methods (`ExecuteAsync`, `LoadMoreAsync`, `CountTotalAsync`, `NavigateForeignKeyAsync`,
  `SaveChangesAsync`) shared the identical lifecycle: raise `IsBusy` → new `_executionCts` → `try body(ct)`
  → `catch OCE` / `catch Exception` → `finally` dispose+null+lower `IsBusy`. Now one
  `RunExclusiveAsync(body, cancelled, failed)` owns it; each call site passes its exact status strings, so
  behavior (including `CancelExecution` seeing the live CTS) is unchanged. The lifecycle reset — the
  error-prone part — now lives in one place. Solution builds 0/0, 142 App tests green.

## Regressions found in QA

- [x] **#3-regression — "Cannot access a disposed object: ConnectionSessionManager" on every query after a
  project switch.** Fix #3 added `ObjectDisposedException.ThrowIf(_disposed)` to `GetOrConnectAsync` to
  close a shutdown race — but the shared manager (created once in `WorkspaceContext`) is **reused** across
  projects, and `OpenProjectAsync`/`NewProjectAsync` called `DisposeAsync()` as a *reset*. Post-#3 that
  retired the manager for good, so the next query threw. Fixed by separating the two lifecycles: new
  `CloseAllAsync()` disposes all live/in-flight sessions but keeps the manager usable; the project-switch
  paths call it instead of `DisposeAsync()` (which stays the shutdown-only, retire-for-good path). The
  schema browser was already reset-safe (no disposed guard), so its `DisposeAsync()` on those paths is
  fine. Tests: +2 (`CloseAll_disposes_sessions_but_leaves_the_manager_usable`,
  `Dispose_retires_the_manager_so_further_connects_throw`). 144 App tests green. **Needs eyeball QA**:
  open/switch a project, then run a query.

## Open bugs (QA-found)

- [x] **Concurrent execution across tabs misbehaves — FIXED.** Diagnosis corrected on investigation: the
  second hypothesis (two tabs sharing one `NpgsqlConnection`) is **disproven by the code** —
  `PostgresQueryExecutor` opens a *fresh pooled connection per call* (`_factory.DataSource.OpenConnectionAsync`)
  and `NpgsqlDataSource` is a thread-safe pool, so two tabs on the same connection id each get a distinct
  physical connection. No "command already in progress", no per-connection serialization needed. The **only**
  defect was the shell-wide `ExecutionViewModel`: one instance with a global `IsBusy` + `_executionCts`,
  always acting on `_ctx.SelectedTab`. A second tab's run hit `if (IsBusy) return;` (silently dropped), the
  Run button/Esc reflected the wrong tab, and Esc cancelled the *other* tab's query.
  - **Fix (per-tab execution + selected-tab façade):** execution state moved onto `EditorTabViewModel`
    (`IsRunning` + its own `CancellationTokenSource`; `BeginRun/EndRun/CancelRun`). `RunExclusiveAsync` now
    takes the target tab and gates on `tab.IsRunning`; all five ops (execute/page/count/FK-nav/save) resolve
    their tab and are per-tab single-flight. `ExecutionViewModel.IsBusy`/`RunButtonText`/`CancelExecution`
    became a **façade over the selected tab** (subscribes `SelectedTabChanged` + the selected tab's
    `IsRunning`), so the XAML binding and Esc handlers are unchanged but now mean "the focused tab." The
    view's `RunAsync`/`RunAllAsync` capture the ran tab and only `RebuildResults` if it's still selected
    (a background completion updates its own VM and shows on switch-back).
  - **Tab-header running indicator:** a rotating arc (`{Syntax.Func}` blue) bound to `IsRunning` in the
    TabStrip item template, so a background run is visible without switching to it.
  - **Tests:** +2 (`ConcurrentExecutionTests`) driving two tabs through a gated `FakeExecutor` (no DB) —
    both run concurrently (the pre-fix single-flight dropped the second), cancel is per-tab (cancelling the
    selected tab leaves the other running), and a second run on the same tab is rejected. 146 App tests
    green; full solution builds 0/0. **Needs eyeball QA** (two tabs, concurrent long queries; Esc/Run act on
    the focused tab; header spinner; switch-back shows background results). Foundation for the deferred
    "Stage E background execution" plan (`docs/background-execution-plan.md`).
