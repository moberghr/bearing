Bearing is 1.0, and it talks to a second engine: **Microsoft SQL Server**. The inline-edit flow — which one
report turned out to contain three separate defects — now saves what is on the screen, including `now()`.

The version is the only thing here that is a decision rather than a change: nothing in the app reads it, the
update feed and the installers work exactly as they did at 0.10, and upgrading from 0.10.3 is the same delta
download as any other release.

### Microsoft SQL Server

Add a connection and pick the engine. Named instances (`HOST\INSTANCE`) are resolved by the SQL Browser
service, Windows authentication is offered where the driver supports it, and Azure SQL's Entra tokens are
minted against the right resource rather than Azure Database for PostgreSQL's.

A SQL Server tab is not the Postgres shape with a different driver under it. The SQL text is built by the
connection's own dialect: `[bracket]` quoting rather than `"double"` — which matters more than it looks,
since SQL Server preserves case and the Postgres rule would have quoted every identifier —
`offset … rows fetch next … rows only` paging, `output inserted.*` where Postgres writes `returning`, and a
count wrapper that declines the shapes a derived table cannot hold instead of asking the server a question it
cannot parse.

Completion, folding and "run the statement under the caret" go through a vendored T-SQL grammar and a T-SQL
scanner, so `GO` separates a batch, a `;` inside a `[delimited name]` does not, and `@variables` and `#temp`
tables tokenize as themselves.

**The write guard reads T-SQL for itself**, and that decided the shape of this release. Running the Postgres
lexer over T-SQL risked *under*-reporting — a batch it could not tokenize would have read as safe on a
connection marked for confirmation, quietly disarming the guard — while the fail-safe answer to that, treating
everything as risky, made a guarded connection confirm on every `SELECT`. So the guard classifies T-SQL on its
own terms and errs towards confirming: a statement it cannot recognise as a read is treated as a write, and a
table called `[delete]` or a string containing `'drop table'` cannot trip it.

Inline editing and foreign-key navigation work, which needed a column's origin — and `SqlDataReader` reports
names where Npgsql reports catalog ids. Result columns carry either form now and the resolvers accept both.
Without it a SQL Server result would have been silently uneditable with no FK badges: nothing failing, just
affordances quietly absent.

### What you see in a cell is what gets saved

Type into a cell and click **✓ Save** without pressing Enter first, and the save wrote the value that was in
the cell *before* you typed. The text in the open editor was discarded.

The grid only told the model about an edit on Enter, Tab or a move to another cell — not when focus left the
grid altogether. So the value sat in an editor nothing on the save path read, the pending-changes toolbar did
not appear until you had clicked somewhere else, and clicking somewhere else was the gesture that dropped the
edit. When a save failed, retyping and saving again re-sent the *first* value, which is why it looked stuck on
one edit.

Anything that reads the pending set now commits the open editor first, and focus leaving the grid commits it
the way a spreadsheet does. **Escape still cancels** — it cancels before focus goes anywhere.

**Ctrl+S inside a cell editor saves the row**, not the script. It used to fall through to the window, which
answered it by writing the script tab to disk: not a no-op, but the wrong save. Ctrl+Alt+Z (discard) and
Ctrl+Alt+P (show SQL) were dead there for the same reason and work now. Every other keystroke — Ctrl+C,
Ctrl+V, the arrows — still belongs to the text being edited.

### An inline edit can be an expression the server evaluates

`now()` typed into a `timestamptz` cell used to be sent as five characters of text, and refused. A cell can
now stand for a server-side expression: `now()`, `current_date`, `current_user`, `gen_random_uuid()`,
`default` and a few more on Postgres; `getdate()`, `sysdatetimeoffset()`, `newid()` and their neighbours on
SQL Server. The cell draws in the function colour and its tooltip says the server will evaluate it.

It is deliberately narrow, because every other value in a generated write is a parameter and that rule is what
keeps the generated SQL safe. A cell is read as an expression only when it sits in a column the driver does
not treat as text **and** the value could not be parsed as that column's type — exactly the cells that were
already drawn amber as unwritable, so no edit that worked before means anything different now. A `text` column
holding the literal `now()` is still that literal. What is emitted is the spelling from a fixed table, never
the string you typed; nothing in that table takes an argument, so nothing can carry a subquery; and a key
predicate refuses one outright.

Each engine has its own table, and there is no translation between them: `now()` typed on a SQL Server
connection stays refused rather than quietly becoming `getdate()`, because the statement that runs has to be
the one the cell shows.

**An UPDATE now reads back the columns the grid displays**, so an expression's value — and a trigger's
rewrite, and an `on update` default — appear as the server actually stored them rather than as what you typed.
Named columns rather than `*`, since a `*` would make a save fail on a table you may update but not read in
full.

### Set value ▸ in the results grid

Right-click ▸ **Set value** offers `NULL` and those expressions, so typing is no longer the only way to reach
them. The item writes exactly what typing would, which is what keeps the rest of the flow identical; a cell in
a text column is skipped and the status line says how many and why.

The list is the connection's, so a Postgres tab offers `now()` and `gen_random_uuid()` while a SQL Server tab
offers `getdate()` and `newid()`. It is deliberately shorter than the list a cell accepts: `uuid_generate_v4()`
needs an extension that may not be installed, and the near-neighbours of `now()` and `getdate()` differ in
precision or in zone in ways a menu cannot explain — all of them stay typeable, none of them are advertised.

### Upgrading

Nothing to do. Existing connections, projects, keybindings and query history are unchanged, and a project file
that has never seen a second engine keeps working exactly as before — which provider a connection uses has
been recorded since long before there was a second one.

### Known limitations

The installers are unsigned, so Windows SmartScreen warns on first run. macOS is Apple Silicon only and
unsigned — install it with `brew install --cask --no-quarantine moberghr/bearing/bearing`.

On SQL Server specifically, stated rather than left to be discovered:

- **Read-only is enforced by Bearing, not by the server.** SQL Server has no session-level "refuse writes" to
  ask for — `ApplicationIntent=ReadOnly` picks a readable secondary, it refuses nothing — so a write Bearing
  cannot see in the SQL, inside a procedure or built as dynamic SQL, still reaches the server. On Postgres the
  server itself refuses. The connection dialog says which of the two you are getting. A role without write
  privileges is the real boundary in either case.
- **The statement timeout is the client cancelling**, not the server refusing, so the server may still be
  finishing the statement for a moment afterwards. Before this release the setting did nothing at all on this
  engine while the status bar reported it.
- **The Activity panel is Postgres-only.** SQL Server has counterparts to `pg_stat_activity`, but a panel that
  can cancel and terminate other people's sessions is not something to map from documentation.
- **Parts of the schema tree are not filled in yet** — sequences, user-defined types, row-level security
  policies, roles and their grants, and the filegroup counterpart of a tablespace. Each has a real SQL Server
  equivalent; each is left out rather than guessed at, because a catalog query is reported only once it has
  been run against a live server. Tables, views, columns, keys, indexes, constraints, triggers, routines and
  sizes are all read.

The SQL Server suites now run against a real SQL Server rather than skipping, which is how several of the
items above stopped being assumptions.
