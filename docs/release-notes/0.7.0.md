Write safety that shows you a number, a schema explorer that stops hiding things, and a CI pipeline — so
"the tests pass" now means something you can check.

### An UPDATE or DELETE tells you how many rows it will touch

The write confirmation used to ask whether you were sure. It now answers the question you were actually
asking: **This will delete 3,412 rows in public.rental.** 3,412 when you expected 1 is unmistakable in a way
no amount of "are you sure" is — it is the number that catches the wrong-tab mistake, because the tab you
meant had one matching row and this one has the whole table.

Three states, and they are deliberately different from each other:

- **a count** — taken against the live connection, from the statement's own WHERE clause;
- **"every row in public.rental"** — the statement has no WHERE at all. Drawn as a warning, and no count is
  taken: the answer is already known, and it is not a number you need;
- **"Could not count the rows this will delete in public.rental in time."** — said out loud rather than left
  blank, because a missing number must not read as a small one.

Three things it refuses to do. It never **connects** — a count is worth less than a credential prompt raised
on top of a confirmation you have not answered yet, so an unconnected tab simply shows no numbers. It never
**blocks** — each count has a deadline and the batch has a smaller total one. And it never **guesses**: a
multi-table `UPDATE … FROM`, a `DELETE … USING`, a CTE or a parameter placeholder is declined outright, so
such a statement shows no number rather than a wrong one.

### See the SQL for pending grid edits — **Ctrl+Alt+P**

Inline edits generate DML, and until now you could see it in exactly one place: the save confirmation, whose
two buttons commit or cancel. There was no way to take the SQL anywhere.

The pending SQL is now viewable at any point while a change is pending, with two routes out — copy it, or
open it in a new editor tab where it can be reviewed, edited and run through the ordinary path, write guard
included. Reading the SQL is not discarding it: the grid's pending state is untouched either way. The window
shows the same statements as the confirmation dialog, from the same object, so the two cannot drift into
showing different SQL for the same edits.

### Export the query log as an audit report

**Command palette ▸ Export query history as an audit report…**, or the button on the History panel. One row
per execution — when, which connection, which environment, which database, the statement, the duration, the
row count, the outcome and its error, and the script it came from — filtered by date range, connection,
environment, or writes only. CSV or xlsx.

Three notes travel with the report, because each of them changes how it should be read: the period actually
covered, that this is one machine's history rather than the server's, and **whether the SQL in it was stored
redacted** (`Settings ▸ Privacy`). In an xlsx they are an **About** sheet; for a CSV they go in a sibling
`<name>.about.txt`, because a note-shaped row inside a CSV breaks it as a table.

Connections are matched by *current* name and by recorded id, so a connection renamed last month still
reports everything it ran under its old name. Matching by name alone silently dropped it, which for "what
ran against production last week" is the wrong answer with no sign that it is wrong.

### Freeze and hide columns

**Right-click a column header**: freeze through this column, unfreeze, hide this column, show all. A
40-column result can be read against a frozen key.

Freeze works on the *display* order, so it still means "everything to the left of this" after you have
dragged a column somewhere else. Hiding is refused for the last visible column — a grid with no columns has
no header left to undo it from.

**Hiding a column hides it from the grid, not from the data.** Exports and full copies still carry it, which
is why "· 2 columns hidden" sits on the result's meta row for as long as anything is: a grid narrowed an
hour ago would otherwise produce a file with columns its own author had never seen. A hidden column may be
an omission; it must never be a silent one.

### Go to table, and go to definition

- **Ctrl+Shift+T** — fuzzy-pick any relation in the loaded schema and reveal it in the tree, expanding
  whatever it takes to get there. Joins the Ctrl+Shift+{J,C,D} family.
- **F12** on the identifier under the caret — an alias resolves to its table, a qualified name to that
  relation, a column reference to that column. Scoped to the statement under the caret, the same way
  execution is: an alias declared in the statement above is not in scope here.

It returns nothing rather than a guess. A keyword, a literal, a CTE name, a function, an alias for a derived
table: no jump. A jump to the wrong table is worse than no jump, because it is silent, and you then read a
schema that is not the one your query is about.

### The schema explorer stops leaving things out

It showed tables, views, columns, indexes, constraints, foreign keys and triggers. Everything else in the
database was invisible — you had to leave for psql to find out a sequence existed.

Per table: **Policies** (row-level security) and **Rules**, alongside the existing folders, and
**Partitions** — the full hierarchy, so a sub-partition of a partition is reachable. Column rows now carry
their default, identity, generated expression, collation and comment, not just the type.

Per database: **Sequences**, **Types** (enum, composite, domain, range), **Extensions**, **Policies**,
**Publications**, **Subscriptions**, **Foreign servers**, **Event triggers**, **Collations**, **Casts**,
**Operators**, **Operator classes** and **Text search** configurations. Empty groups do not appear, so an
ordinary database does not grow thirteen empty folders.

Under the server: **Roles**, each expanding to its members and its grants, and **Tablespaces**.

And **Functions and Procedures are now separate groups**. A CALL-only routine was filed under Functions, and
CALL versus SELECT is a difference you find out about by getting an error.

Each kind is read independently, so one catalog a role cannot see costs that one group rather than all of
them.

### CI

Every pull request and every push to main now builds and runs the suite on **Ubuntu with a real PostgreSQL**
and on **Windows**. Roughly 150 live catalog tests had been skipping quietly on every machine that lacked a
database, and a workbook readback that never ran at all. Both now run somewhere, on every change, and the
job summary lists skipped tests **by name** — a skip is otherwise invisible, and "0 failed" over a suite that
skipped its whole database half is exactly the reassurance this was meant to remove.

That turned up five defects the suite had not, and they are in this release:

- **A concurrently dropped relation lost every object's size in the schema tree.** `pg_class` is read under
  the query's snapshot but `pg_total_relation_size` reads stats files, which are not — so a table someone
  else drops mid-read is still listed and has no size, and the reader threw on it. Such a row is now skipped
  rather than reported as 0 bytes, which would have claimed the table was empty.
- **Multi-sheet workbooks were never actually verified.** The check that reads our xlsx back through
  LibreOffice was passing a sheet index in a filter slot that means *first line number*, so it read sheet one
  three times while believing it had asked for three different sheets. It now exports every sheet and looks
  each one up by name — which checks the names too.
- Line endings are normalised, so 40 formatter tests no longer depend on the checkout's autocrlf setting.
- A daylight-saving boundary test read the machine's local zone and so skipped on a UTC runner — inert
  exactly where the bug it covers was found.
- `build/test-db.sh` was not executable.

The release pipeline gained a database of its own, so the catalog and temporal-mapping suites now run before
anything is published rather than skipping — and a release ticked **Set as a pre-release** is now uploaded as
one. That flag is what keeps a beta from being offered to every installed copy, and it was being dropped.

### Smaller things

- **A policy row under its own table no longer repeats the table's name.** The folder above it already says
  which table it is on, and the panel is narrow.
- **Switching a tab's database no longer rebuilds the connection pool.** Sessions are keyed by connection
  *and* database, so two tabs on different databases of one server keep independent pools and switching back
  and forth reuses both — instead of discarding a working pool, its TLS handshake and all its server-side
  state.

### Upgrading

Nothing to do. No settings, projects or keybindings change, and the new bindings — Ctrl+Shift+T, F12,
Ctrl+Alt+P — are defaults you can override in `keybindings.json` as usual.

The query log's schema is migrated in place, once, on first start, to hold the connection id and environment
the audit report needs. Older entries keep the name they were written with, and the report matches on both.

### Known limitations

Unchanged: the installers are unsigned, so Windows SmartScreen warns on first run; there is no macOS
package; and syntax colouring is verified by eye rather than by tests.

Row counts for a write confirmation need a connected tab — an unconnected one shows the statements without
numbers, by design (above).
