Bearing has a command line. **`bearing`** queries the connections you have marked for it — read-only, and
without the caller ever learning the host, the user, the database or the password. It is meant for AI
agents, and it works just as well from a shell or a script.

```console
$ bearing connections
$ bearing tables reporting --schema public
$ bearing describe reporting public.payment
$ bearing query reporting "select count(*) from payment"
$ bearing query reporting --file monthly.sql --out report.xlsx
```

Typing `bearing` on its own still opens the window, as before. `bearing --help` lists everything.

### Nothing is reachable until you say so

Two things must both be true. You ticked **"Let the `bearing` command query this connection, read-only"** in
the connection dialog's Safety group — off for every connection that exists and every one that ever existed
— and the credential can be obtained without a window, so a connection that asks for its password each
session is listed as unavailable with that reason. An exposed connection is marked in the connections panel,
beside where it says which server it is.

The mark travels in the project file, so opening a shared project takes its connections' settings whole.
Copying a connection to the clipboard deliberately does **not** carry it: losing a restriction announces
itself the first time a write is refused, while a permission that arrived with a paste is invisible until
something uses it.

### What stops a query doing damage

Four things, and the honest order of how much each is worth.

**Only reads are sent at all.** A statement runs only if its leading keyword is one this engine calls a read.
Everything else is refused before it reaches the server — `SET`, `BEGIN`, `COMMIT`, and any shape nobody
listed. That last part is the point: a SQL construct we have not thought about defaults to refused.

**The session is opened read-only anyway**, which on PostgreSQL the server enforces, so a write the client
could not see — a volatile function, dynamic SQL — is refused there too. On SQL Server there is no session
read-only to ask for, so the first layer is the whole of it, and the connection dialog says which of the two
you have.

**A handful of functions are refused inside otherwise-ordinary reads** — reading the server's filesystem,
killing its sessions, changing this session's settings. Read-only never bounded those, because they are
reads; just not of your data.

**Three catalogs are not readable at all**, for what they hold rather than what they are: password hashes, a
subscription's connection string, and a foreign server's stored password.

The last two stop accidents rather than a determined caller, and it would be dishonest to say otherwise. The
thing that is a wall is the database role the connection authenticates as. If you expose a connection, point
it at a role that cannot do the damage in the first place — `docs/CLI.md` has a `create role agent_ro …`
recipe to paste.

**A statement timeout is filled in** (30 seconds) when the connection does not set one, so a runaway query
cannot outlive the caller. A limit you set yourself is kept, however long.

### It is in your history, refusals included

Every query the command runs is written to the same local log the app keeps, marked with its origin, so an
agent's statements sit beside your own and are told apart at a glance:

```
12:04  [cli] select count(*) from payment      88 ms
12:04        select * from film limit 100      12 ms
```

**A refused statement is recorded too.** Strictly nothing ran — but the caller is not the person at the
keyboard, and "an agent tried to lift read-only and was stopped" is the most useful line this log can hold.
Your retention and literal-redaction settings apply exactly as they do to your own statements, and the audit
export carries the origin so "what ran against production last week" includes what an agent ran and says so.

`tables` and `describe` are not logged. They read the catalog, which is not a record of what someone ran.

### Installing it

`bearing` ships inside Bearing's own package, so it installs, updates and uninstalls with the app and can
never drift from the project format it reads.

- **Windows** — the installer puts the install directory on your user `PATH` and takes it off again when you
  uninstall. You may need a new terminal for it to be found.
- **macOS** — the Homebrew cask puts it on `PATH`.
- **Linux** — beside the app in the install directory.

Inside that directory there are now two executables: `bearing` (the command) and `bearing-app` (the window).
A command has to be a console program, and the name you already know should be the one you can type — so
`bearing` with no arguments starts the window, and nothing about opening Bearing changes.

### Also in this release

**Exports of a single statement stream.** `bearing query … --out report.csv` writes rows to the file a batch
at a time, so it can be pointed at a table larger than the process. Written to a temp file and moved into
place, so a read that fails part-way leaves no file rather than a convincing fraction of one. A workbook
still has to be built whole, so `.xlsx` stays bounded by memory.

**A write-guard fix that affects the editor, not just the command.** T-SQL does not require a separator
between statements, so `select 1 drop table t` is one statement whose leading word is `SELECT` — and a
connection marked for write confirmation did not prompt for it. A risky verb anywhere in a statement's
top-level words now counts. The cost is that a column genuinely named after a verb asks for a confirmation
it does not need; `[copy]` is the escape.

**Query plans say when they are unavailable.** `explain` is PostgreSQL's only — SQL Server reports plans in a
form Bearing does not read yet — and both the app and the command now say so instead of sending a statement
the server will reject.

### Upgrading

Nothing to do, and nothing to decide. No connection becomes reachable from outside until you tick the box,
and no existing setting, project, script or keybinding changes.

The GUI executable is renamed, so the first update across this version rewrites your Start Menu shortcut.
The update identity is unchanged — installed copies update normally.

### Known limitations

- The installers are unsigned, and macOS is Apple Silicon only. Unchanged from 1.0.
- **`bearing` runs as you.** It reads the same project file and the same keychain the app does, so it is not
  a sandbox and nothing here should be read as one. What the per-connection mark gates is which connections
  a caller can *find*; read-only is what bounds what it can do with them, and a restricted database role is
  what bounds the rest.
- Every invocation is a fresh process and therefore a fresh connection — right for a command called a few
  times a minute, wrong inside a loop. Prefer one well-aimed query with an aggregate over many small ones.
- Writing from outside is not supported and is not a missing flag: what makes a write safe in the app is a
  human reading the row count before confirming it, and there is nobody to ask.
