Two safety settings that the **server** enforces, a panel that finally lets you look at what a server is
doing, and a schema tree that stopped growing sideways.

### A connection can be read-only

Tick **Read-only** on a connection and its sessions start with `default_transaction_read_only=on`, so the
server refuses writes on them. Bearing refuses a recognised write before sending it — a refusal, not a
confirmation, because there is nothing to confirm when the answer is already no — and the grid stops
offering inline edits, showing the reason on the lock chip it already had. The Production preset turns it
on for new connections.

The client-side half is the early one and never the enforcement. A lexer cannot see a function that writes,
dynamic SQL inside a `DO` block, or `COPY … TO`; the server catches all three. Both halves are wanted.

**It is described as what it is, and not as more.** `default_transaction_read_only` is a setting a session
can change, so `SET default_transaction_read_only = off` or `BEGIN READ WRITE` lifts it. It stops mistakes —
the wrong tab, the wrong window, the statement you meant to run against staging. The boundary nobody can
lift is a role without write privileges, and that is your server admin's to grant.

### A per-connection statement timeout

Seconds, `0` for no limit. 0.5.3 removed the *client-side* timeout, which fixed the waiting and not the
query: the statement carried on running on the server long after Bearing had stopped watching it. This is
the other half — the server cancels it.

When a statement comes back cancelled, the message now says which of the three things happened: you pressed
Esc, this connection's timeout expired (and it names the limit), or something outside Bearing cancelled it.
They were indistinguishable before, and the third one is the one you would never have guessed.

**Both settings ride the connection's startup packet, not a `SET`.** A connection pool holds up to ten
physical connections, opened and pruned underneath you while a session is live, so a `SET` reaches the one
socket it was issued on — and whether a statement was read-only would depend on which socket it landed on.
The startup packet is applied to every one of them before it can run anything.

### Server activity — see what is running, and stop it

A new panel on the side rail. It lists the backends on the server you are connected to, refreshed every two
and a half seconds while it is open and not at all when it is not. A row carries the pid, the state and how
long; selecting it shows the statement, formatted and syntax-coloured, in the same read-only viewer the
history preview uses. Right-click gives **Cancel statement** and **Terminate session**, both confirmed.

This closes something 0.5.3 opened and could not: a query that outran its timeout is told it "may still be
running on the server", and until now there was no way to look.

- **It shows your own database, and the sessions doing something.** `pg_stat_activity` is cluster-wide, so
  the honest unfiltered answer on a production host is every session on the machine, most of them a pooled
  connection sitting between statements. Two checkboxes widen it when you are hunting whoever holds the
  lock. **`idle in transaction` is never hidden** — it holds locks, and it is the row the panel most exists
  to show.
- **Terminate is refused on a read-only connection; Cancel is not.** Neither is blocked by the read-only
  setting on its own, so the refusal is ours. Cancelling stops a statement and leaves the session, and it is
  most wanted on exactly the production connection most likely to be read-only.
- **A role that cannot see other sessions is told so**, rather than shown a quiet server. Measured against
  PostgreSQL 18: a role without `pg_read_all_stats` does not receive other sessions as rows with the details
  blanked out — it does not receive the rows. Nothing in a short list can tell you that, so the panel asks
  the server outright and says which answer it is giving you.

### The schema tree has two shapes

A database's children had grown to a flat run of up to seventeen sibling groups, a kind at a time. There are
two shapes now, toggled from the panel header and remembered as a setting:

- **Simple** — the shape you have: relations inline, one click from a database to a table, with the long
  tail behind a single **Other objects** bucket.
- **Full** — schema-first. **Schemas** → a schema → Tables, Views, Functions, Procedures and that schema's
  own kinds, with what belongs to the database rather than to any schema under **Administer**.

Simple stays the default. Full is the better shape on a server whose schemas mean something, and it is three
clicks to a table — so it is offered rather than imposed.

Switching re-arranges what has already been read and fetches nothing.

**A group that is empty now says so.** A kind whose read came back with nothing shows an em-dash rather than
being left out, so inside a schema the set of rows is fixed and can be scanned. A group whose read has not
landed yet is still not drawn at all — the dash means "asked, and there are none", never "not yet".

### A database with no readable size says so

It rendered blank, which looked identical to a size that had not arrived (the read is deliberately late), a
read that failed, and a database that genuinely has none. It now reads **"size not visible"**, with the
missing `CONNECT` privilege in the tooltip — the only cause that was actually checked.

### Smaller things

- **Copying a connection carried every field except its TLS mode.** A Verify Full connection pasted as one
  on the driver default. The test that was supposed to catch this listed ten fields by hand and had omitted
  the same one; it reads the record itself now, so the next field added fails until it is carried.
- **An idle backend no longer reports a running time.** PostgreSQL keeps the *last* statement's start time
  after that statement finishes, so the obvious arithmetic gave a growing duration for a session executing
  nothing — a backend that had sat `idle in transaction` for 41 minutes read as one that had been running a
  statement for 41 minutes. It now says how long it has been in the state it is in, which is the number that
  row is worth reading, and sessions actually executing something sort to the top.
- **The activity panel's SQL pane no longer resets while you read it.** The list was rebuilt on every poll,
  which took the selection with it, so the statement re-rendered — losing the caret, any selection and the
  scroll position — twice every few seconds.

### Upgrading

Nothing to do. Existing connections are not read-only and have no timeout, and the schema tree opens in the
shape it already had. Both connection settings live in the connection dialog, and the tree's shape is in
**Settings ▸ Connections**.

### Known limitations

Unchanged: the installers are unsigned, so Windows SmartScreen warns on first run; there is no macOS
package; and syntax colouring is verified by eye rather than by tests.

The activity panel lists client backends, not the server's own processes, and it cannot show you a session
your role is not allowed to see — it tells you that is the case instead.
