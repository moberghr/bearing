A fold-gutter fix for anyone whose scripts use Windows line endings — which, on Windows, is most people.

### Statement folding works on CRLF files

Open a script with several multi-line queries and the fold gutter was empty: no `[-]` to click, nothing to
collapse by mouse. Reported by a user of 0.5.0, and the cause was line endings.

A foldable region starts at the end of its statement's first line. That position was being calculated as the
offset of the `\n` — which is right for a file saved with Unix line endings, where it is exactly where the
line ends, and one character too far along for a file saved with Windows ones, where the line ends at the
`\r` before it. The gutter matches a fold to the line it starts on, found nothing on any line, and drew no
markers.

Everything else about folding was working the whole time, which is why this took a real file to find:
`Fold statement` and `Fold all` collapsed correctly from the keyboard and the command palette, the folds were
counted correctly internally, and the statement highlight was in the right place. The only thing missing was
the control you click — no error, no warning, just an empty gutter.

If you were affected, nothing needs doing beyond updating: the fix is in how regions are measured, so your
scripts open with their fold markers present.

### Also

- Folds are now rebuilt explicitly when a tab's buffer is loaded, rather than as a side effect of the
  editor's change notification. Every other piece of per-buffer state — the statement highlight, the tab's
  font zoom, its results — was already rebuilt by name; folding was the one that depended on an event
  firing, and an event that does not fire leaves an empty gutter with nothing to say so.

### Upgrading

Nothing to do. No settings, projects or keybindings change.

### Known limitations

Unchanged from 0.5.0: the installers are unsigned, so Windows SmartScreen warns on first run; there is no
macOS package; and syntax colouring is verified by eye rather than by tests.
