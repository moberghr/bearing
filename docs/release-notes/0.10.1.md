One fix: `TRUE` and `FALSE` are coloured in the editor, like the `NULL` standing beside them.

### true and false are no longer plain text

A boolean literal was drawn in the ordinary text colour while everything around it was coloured — including
the `null` in the very same predicate. `where t.is_financial = FALSE` read as though the `FALSE` were an
identifier rather than a value, which is the one thing it is not.

Nothing in Bearing had ever tagged them. Syntax colouring comes from the SQL grammar VS Code ships, and that
grammar has no rule for boolean literals at all — `true` and `false` appear in none of its patterns. The
`null` next to them is coloured only by accident of an unrelated rule that happens to catch it. VS Code draws
booleans the same plain way for the same reason.

They are tagged as the literals they are now, and land on the same colour as `null`, as they do in DBeaver.
The rule is added over the packaged grammar rather than replacing it, so it applies everywhere SQL is shown:
the editor, the history panel's preview, the SQL preview before a write, and the statement another session is
running in the Activity panel.

A `true` inside a string or a comment is left alone, and a column named `is_true` is still a column.

### Upgrading

Nothing to do. No settings, projects or keybindings change, and nothing about your data, your queries or your
exports is affected — this changes only what the editor draws.

### Known limitations

Unchanged: the installers are unsigned, so Windows SmartScreen warns on first run, and there is no macOS
package.

Syntax colouring is still verified by eye rather than by tests, with one exception as of this release: which
scope each of `true`, `false` and `null` is tagged with, and that the theme resolves all three to one colour,
is asserted against the tokenizer directly. What no test here can say is that the result looks right on
screen.
