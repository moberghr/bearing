**Queries now compute in your time zone, as they do in DBeaver.** If a query casts or truncates a
`timestamptz`, it can return different results after this update. That change is the fix.

### What was wrong

Postgres converts an instant to a clock time (`::timestamp`, `::date`, `date_trunc('day', …)`, or
subtracting a `timestamp` from a `timestamptz`) in the *session's* time zone. Bearing never set one, so every
session kept the server's own zone, which is UTC on RDS. DBeaver sends your machine's zone. The same query
against the same database could therefore return results two hours apart in the two tools, and the grid
could show local times above SQL that had run in UTC.

```sql
select timestamptz '2026-09-18 18:00:00+00'::timestamp;
-- 1.2.0:  2026-09-18 18:00:00   (the server's zone, UTC)
-- 1.3.0:  2026-09-18 20:00:00   (Europe/Zagreb, as in DBeaver)
```

Plain `timestamptz` values shown in the grid were never affected. Only calculations inside the SQL were.

### A time zone per connection

The connection dialog has a new **Session time zone** setting:

- **This machine's zone**, the default. It is sent under its standard name (`Europe/Zagreb`), which the
  server accepts, even on Windows, which names it differently.
- **The server's own zone**, which is how 1.2.0 behaved.
- **A specific zone**, e.g. `UTC`, for a connection whose results must not depend on who runs the query.

The status bar's tooltip now names the zone the session computes in, so a mismatch is visible. PostgreSQL
only: SQL Server has no per-session zone, so the setting is not offered there.

### Fixed

- **Copy as ▸ SQL and the SQL export now mark `timestamptz` values as UTC**
  (`'2026-09-18 15:00:00+00:00'`). Without the offset, the copied text would be read in the new session
  zone and land hours away from the original value.

### Upgrading

Every existing PostgreSQL connection starts computing in your machine's zone. To keep the old behaviour for
a connection, set its Session time zone to **The server's own zone**. A connection that already had a
`Timezone` entry in its options keeps that zone.

The `bearing` command uses each connection's setting too, so by default it computes in the zone of the
machine it runs on.
